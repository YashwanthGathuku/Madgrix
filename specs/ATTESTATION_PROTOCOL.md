# Attestation Protocol (v0.1 — hardening in parallel)

**Status:** CONTRACT (may harden in parallel with implementation of specs 1/3/5).
The core decisions — standards reuse, the single custom object, the digest
model — are frozen. **[OPEN]** marks undecided points.

## 1. Purpose

Make every promotion **independently verifiable offline** without inventing a
proprietary ledger format. We reuse established supply-chain machinery and add
exactly one custom semantic object. Our contribution is not "we invented
signatures" — it is **exact-state authorization applied to autonomous agent
code promotion**.

## 2. Standards mapping

| Need | Standard | How we use it |
|---|---|---|
| Bind metadata to an immutable subject | **in-toto Attestation Framework** | Every attestation is an in-toto Statement: `_type`, `subject[]` (digest set), `predicateType`, `predicate`. The framework's fundamental rule — metadata binds to a subject digest — is exactly our exact-state requirement. |
| Test results | **in-toto test-result predicate** (existing) | Subject = candidate SHA-256; predicate carries test configuration digest + PASS/WARN/FAIL. |
| Verification results | **in-toto software-verification-result predicate** (existing) | Records which policy verified the artifact (`policy_sha256`). |
| Trust boundary | **SLSA** | Provenance MUST be generated by the control plane, not by contender-controlled steps; signing secrets MUST NOT be available to contender steps. |
| Signing & offline verification | **DSSE + Sigstore** | Attestations wrapped as DSSE envelopes; Sigstore for offline-verifiable bundles. The demo ends with `$ verify promotion.bundle` (see §7). |

**MUST NOT** invent a proprietary attestation envelope, a custom signature
scheme, or a bespoke ledger format for anything the table above covers.

## 3. Attestation chain

```
WORK INTENT
  (task_hash, frozen task record — spec 1 §5)
    │
    ▼
in-toto LINK
  materials = baseline commit digest
  subject   = candidate (git_commit + tree_sha256)
    │
    ▼
TEST RESULT            (in-toto predicate)
  subject = candidate SHA-256
  config  = test-policy digest
  result  = PASS / WARN / FAIL
    │
    ▼
VERIFICATION RESULT    (in-toto predicate)
  subject = candidate SHA-256
  policy  = selector-policy digest
  result  = PASSED / FAILED
    │
    ▼
PROMOTION AUTHORITY    (AgentPromotionAuthority/v1 — §4, the ONE custom object)
  subject = exact final tree
  single_use, destination-bound, nonce
    │
    ▼
SHIP RECORD
  (canonical repo write + permit consumption — spec 1 §11)
```

Each link's `subject` digests MUST chain: the test result's subject MUST equal
the link's subject; the promotion authority's subject MUST equal the verified
candidate's tree digest. A verifier recomputes the chain; any break fails
verification.

## 4. The one custom object: AgentPromotionAuthority/v1

```jsonc
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [
    { "digest": { "sha256": "<tree_sha256 of the exact final tree>" } }
  ],
  "predicateType": "https://seam.dev/AgentPromotionAuthority/v1",
  "predicate": {
    "intent": {
      "digest": "<task_hash>"            // spec 1 §5
    },
    "baseline": {
      "git_commit": "<baseline git SHA>"
    },
    "candidate": {
      "repo": "<contender fork repo name>",
      "commit": "<candidate git SHA>",
      "tree_sha256": "<tree_sha256>"    // MUST equal subject digest
    },
    "evaluation": {
      "bundle_sha256": "<evaluation_bundle_hash>"  // spec 1 §7
    },
    "verification": {
      "result": "PASSED",
      "policy_sha256": "<selector_policy_hash>"
    },
    "destination": {
      "repo": "<canonical repo>",
      "expected_parent": "<destination HEAD at permit issue>"
    },
    "authority": {
      "nonce": "<random 256-bit, hex>",
      "single_use": true,
      "permit_id": "<SHA256(task_hash||baseline||tree||eval_bundle||policy||expected_parent)>",
      "issued_at": "2026-10-01T18:00:00Z"
    }
  }
}
```

Wrapped as a **DSSE envelope** (`payloadType:
application/vnd.in-toto+json`), signed by the promotion authority key held in
the control plane.

Rules:
- `predicate.candidate.tree_sha256` MUST equal `subject[0].digest.sha256`.
- `predicate.authority.permit_id` MUST equal the recomputation from spec 1 §10.
- `single_use` is always `true`; there is no multi-use promotion authority.
- The `nonce` MUST be fresh per permit (defense against cross-task replay).

## 5. Digest model: both identities, always

Every code identity in the chain carries BOTH:

- `git_commit`: the Git object ID (what developers and Artifacts use), AND
- `tree_sha256`: SHA-256 over the canonical tree (what the cryptography binds).

Rationale: the Git SHA-1 namespace is the platform's native identity, but the
authorization binds the SHA-256 tree digest. Never treat the Git object ID as
the sole cryptographic identity of "the code that ships".

## 6. Signing

- Signatures MUST be DSSE-compatible. v1 uses Sigstore for offline-verifiable
  bundles (`promotion.bundle`).
- The signing key lives in the **control plane only** (SLSA trust boundary,
  spec 3 §2). Contender sandboxes, evaluator sandboxes, reviewers, and the
  verdict plane MUST NOT have access to it.
- Key management (rotation, transparency log) follows Sigstore practice.
  **[OPEN]** Fulcio vs. long-lived key for the competition demo; the demo
  verifier MUST work fully offline regardless.

## 7. Verification procedure & demo transcript

`$ verify promotion.bundle` MUST perform, in order, and print:

```
$ verify promotion.bundle

subject digest ........ OK      # subject digest recomputes from the tree
candidate digest ...... OK      # candidate commit+tree match the attested digests
chain integrity ....... OK      # link → test → verification → authority subjects chain
hidden evaluation ..... PASSED  # verification predicate result
policy digest ......... OK      # selector policy hash matches the frozen policy
destination parent .... OK      # expected_parent matches the recorded ship parent
signature ............. VALID   # DSSE signature verifies (offline)
promotion authority ... CONSUMED ONCE   # permit_id present exactly once in the ledger

VERIFIED
```

Any line failing → overall `NOT VERIFIED` with the failing line(s) named.
The verifier MUST be runnable offline (bundle carries everything it needs).

Failure semantics:

| Tamper | Detected at |
|---|---|
| Tree differs from attested digest | `subject digest` |
| Shipped commit ≠ reviewed candidate | `candidate digest` |
| Evaluation bundle substituted | `hidden evaluation` / `policy digest` |
| Promotion replayed | `promotion authority` (permit already consumed) |
| Signature forged | `signature` |
